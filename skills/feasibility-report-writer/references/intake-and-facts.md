# 材料摄取与事实底稿（Stage 0）

把用户资料变成一份**可溯源、可后续引用**的事实底稿，是后续调研与撰写的基础。核心原则：先提取再提问，标注证据状态，缺口显式留痕。

## 1. 摄取顺序

1. **对话内容**：用户口述的项目定位、问题、方法、团队、指标——先提取，不重复问。
2. **用户文件**：`.doc/.docx/.pptx` 用 `{baseDir}/scripts/office_to_markdown.py` 转文本（输出到工作目录的 `outputs/intake`）；`.pdf/.md/.txt` 直接读；项目目录按需读关键文件。
3. **不读**：第三方依赖、`node_modules`、构建产物、密钥/令牌/个人敏感信息；代码中未调用分支与注释不视为已实现功能。

转换命令（在工作目录下运行，产物落 `outputs/intake`）：
```bash
python3 {baseDir}/scripts/office_to_markdown.py <files...> \
  --output-dir outputs/intake --manifest outputs/intake/office_manifest.json
```

## 2. 必须确认的关键信息（缺则影响立项）

- **研究对象与场景**：针对什么对象、什么生产/应用场景；
- **核心问题**：现有方案的不足、要解决的关键问题；
- **研究内容与方法**：拟研发什么、用什么技术路线；
- **团队与基础**：承担单位、负责人、合作单位、前期储备；
- **预期指标**：技术指标、效益、成果数量；
- **周期与预算**：研究起止年月、总预算、项目类型。

输入过短时，**只问最影响立项判断的 3–5 个组合问题**，不问申请人/版式等不影响内容的问题。

## 3. 证据状态标注（每条关键信息必标）

| 状态 | 含义 | 写作时 |
|---|---|---|
| `用户已确认` | 用户明确提供或确认 | 可直接写入正文 |
| `资料有据` | 可定位到用户文件/可靠来源 | 可写入，注明来源 |
| `合理推断` | 为组织方案作的推断，尚待确认 | 不得写成事实，标 `【待确认：…】` |
| `待确认` | 影响可实施性或立项判断的缺口 | 必须留 `【待确认：…】`，列入待确认清单 |
| `建议方案` | 研发建议，非既有内容 | 须用户确认后才能并入，单列 |

**红线**：不得把「合理推断」「建议方案」直接写成已经实现或已经具备的事实。用户要求一次成稿时可继续写草案，但保留 `【待确认：…】`，不偷偷补造细节。

## 4. 事实底稿格式（`outputs/project_brief.md`）

```markdown
# 项目事实底稿

## 项目画像
- 项目名称：[…]
- 承担单位：[…]
- 合作单位：[…]
- 负责人：[…]
- 研究起止：[…]
- 总预算：[…]
- 项目类型：[如 公益类科技计划项目]

## 关键信息（带证据状态）
### 研究对象与场景
- [信息] 　状态：资料有据（来源：xxx.doc 第 N 段）

### 核心问题
- [信息] 　状态：用户已确认

### 研究内容与方法
- [信息] 　状态：合理推断　【待确认：…】

### 团队与基础
- [信息] 　状态：待确认　【待确认：负责人近 3 年论文清单】

### 预期指标
- [信息] 　状态：建议方案（须用户确认）

## 待确认项清单
1. ……
2. ……

## 已具备材料清单
- 文件路径 / 类型 / 摄取时间 / 关键内容定位
```

## 5. 与后续阶段的衔接

- 事实底稿的「证据状态」直接决定正文怎么写：`用户已确认/资料有据` 可成文，其余留痕；
- 「待确认项」汇总成 Stage 1 大纲的缺口标注与对用户的确认问题；
- 标注为「资料有据」的来源，进入 Stage 2 信源清单的「用户提供材料」类型。
