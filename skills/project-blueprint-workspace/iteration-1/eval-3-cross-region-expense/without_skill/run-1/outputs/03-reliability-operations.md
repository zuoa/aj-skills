# 03. 可靠性与运维蓝图

## 1. 目标解释

- 生产 RPO ≤ 15 分钟：灾难切换后，可接受的数据丢失窗口不超过 15 分钟。
- 生产 RTO ≤ 2 小时：从宣布灾难到核心服务恢复可用不超过 2 小时。
- “核心服务”首版定义为登录、费用/发票读取、提交与审批、预算校验；支付发起可短时降级为排队，但不得丢失或重复执行。
- 指标必须按每个区域独立验证；欧盟恢复位置、备份和运维数据仍在欧盟。

**[BUSINESS]** 确认支付发起、管理员配置、通知和报表是否也必须纳入 2 小时核心范围。  
**[LEGAL]** 确认中国与美国区灾备边界以及合同对“区域”的精确定义。

## 2. 部署与灾备拓扑

每个数据平面：

- 主站点跨至少 2–3 个可用区；负载均衡、应用和队列避免单可用区依赖。
- 关系库同步多可用区高可用；到同法域灾备位置持续复制，复制延迟告警阈值低于 15 分钟。
- 对象存储启用版本控制，并复制到同法域灾备位置；验证发票对象与数据库引用的一致恢复点。
- 每 15 分钟或更频繁产生可恢复数据库增量/PITR；定期全量备份；备份不可变、加密、与生产删除权限隔离。
- 基础设施、服务配置和恢复清单代码化；容器/制品跨站点预置，减少恢复时下载依赖。

采用区域内 warm-standby：网络、密钥、核心数据库副本、对象副本与最小运行能力预置；灾难时扩容并切换流量。此方案较容易在 2 小时内恢复，同时控制常态成本。

## 3. 恢复顺序

1. 事件指挥官宣布灾难、冻结高风险写操作并记录恢复基准点。
2. 验证灾备身份、网络、KMS/秘密、数据库和对象存储可用性。
3. 提升数据库副本或执行 PITR；校验租户数、关键账本和附件引用。
4. 恢复 Identity/Tenant、Expense、Approval、Budget，再恢复 Invoice worker、Payment、Notification。
5. 切换区域流量；对客户端启用退避和幂等重试。
6. 支付恢复前先核对 outbox、供应商结果与 webhook inbox，未知状态人工处理。
7. 验证审计连续性、关键 SLI 与抽样业务流程，宣布恢复并启动事后复盘。

## 4. SLO 与可观测性候选

| 信号 | 候选目标/告警 |
|---|---|
| 核心 API 可用性 | 月度 99.9% 候选；按区、按租户分片观测 |
| 交互 API 延迟 | p95 < 500 ms 候选，不含文件上传和第三方耗时 |
| 审批事件延迟 | 99% 在 60 秒内完成内部状态传播 |
| OCR | 独立队列 SLO，不阻塞已上传原件查看 |
| 灾备复制延迟 | > 5 分钟预警，接近 15 分钟升级为事件 |
| 支付未知状态 | 实时告警；禁止自动重复发起 |

**[BUSINESS]** 与客户合同对齐正式 SLO、维护窗口和赔偿边界；候选值不是承诺。

## 5. 容量与降级

- 发票上传采用对象存储直传与每租户配额；OCR worker 按区域队列扩缩容。
- 第三方 IdP 故障时保留现有有效会话；不默认提供绕过企业 SSO 的本地登录。
- 支付方故障时支付指令持久排队，界面显示“处理中”；熔断后人工对账。
- 通知故障不阻断审批事务；报表与全文搜索可只读或延迟。
- 对热点租户设置公平队列/限流，防止 noisy neighbor 影响其他租户。

## 6. 演练与验收

- 上线前执行一次完整区域恢复演练，并记录实际 RPO/RTO、步骤耗时、数据校验和缺陷。
- 每季度恢复随机数据库与对象样本；至少每半年执行区域切换演练。
- 每月验证备份可读性、复制延迟和恢复凭证；恢复账号不能依赖故障中的同一身份系统。
- 演练覆盖数据库误删、对象误删、区域不可用、KMS 访问故障及支付回调中断。

若实测超过目标，必须记录差距、负责人和期限；不能仅凭架构配置宣称达标。
