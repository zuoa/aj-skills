# 验证与交付计划

## 1. 先验证，再扩建

### 阶段 A：问题与规则验证

目标：确认真正需要减少的工作，以及预约必须遵守的规则。

建议材料：

- 用当前蓝图访谈若干具有代表性的独立教练；样本数量由可获得性决定，不预设结论。
- 收集匿名化的真实课程、排期、预约沟通示例。
- 用纸面或低保真原型走查首次发布、学员预约、取消和冲突场景。
- 记录不同教练之间相同与不同的规则，判断哪些属于首发目标细分市场。

退出条件：阻塞项已决定，核心流程能覆盖目标教练的主要预约场景，MVP 边界得到认可。

### 阶段 B：可用原型

目标：验证信息架构和手机预约交互，不承诺完整后端。

原型至少覆盖：

- 教练创建课程与设置时间。
- 学员选择时段与提交信息。
- 成功、时段被抢、暂无时间、表单错误等关键状态。
- 教练查看预约和发起取消。

退出条件：测试对象无需口头引导即可完成主要任务，主要误解被记录并修正。

### 阶段 C：端到端 MVP

按纵向切片交付，每个切片都包含界面、规则、数据与验证：

1. 教练账号与数据隔离。
2. 课程创建、发布及公开展示。
3. 可用时段设置与手机端浏览。
4. 并发安全的预约创建与结果页。
5. 教练预约列表、详情与已确认的状态操作。
6. 必要通知、操作记录与基本支持能力。
7. 隐私、安全、恢复和上线准备。

### 阶段 D：小范围试用

目标：观察真实排期周期中的行为，而非只验证演示路径。

- 选择与目标细分一致、愿意反馈的教练。
- 明确试用期支持方式和问题升级路径。
- 观察预约完成、失败、取消、手工绕过和继续使用情况。
- 用证据决定支付、日历集成、团课等后续功能优先级。

## 2. MVP 验收框架

### 教练发布

- 教练能创建并发布一个满足规则的课程。
- 未满足必填条件时不能发布，且能看到原因。
- 停用课程后不再接受新预约，已有预约处理符合已确认规则。

### 学员预约

- 可用时段在目标手机浏览器中清晰可选。
- 有效提交只产生一个预约。
- 两个并发请求不能成功占用同一不可共享资源。
- 成功页显示足以核对预约的信息，不泄露内部或他人数据。
- 失败后学员知道下一步能做什么。

### 教练管理

- 教练只能查看和操作自己的数据。
- 列表与详情中的时间、课程和状态一致。
- 状态变更保存操作者与时间，并遵循确认过的转换规则。

### 运营质量

- 通知失败不会改变预约真实状态，并可被发现。
- 对关键路径有最少但足够的日志与监控。
- 备份和恢复流程在上线前实际演练。
- 隐私说明、数据请求与账号停用处理有明确负责人。

## 3. 测试重点

- 课程与时段的创建、编辑、停用及权限测试。
- 时间边界：跨日、夏令时（若目标市场涉及）、时区展示、预约临界点。
- 并发：同一时段同时提交、重复点击、请求重试。
- 状态机：所有允许和禁止的状态转换。
- 移动端：慢网络、刷新、后退、表单恢复、常见屏幕尺寸。
- 安全：越权访问、枚举预约标识、恶意输入、失效链接。
- 通知：延迟、失败、重复发送和信息最小化。

## 4. 发布前清单

- 阻塞业务规则均有负责人和结论。
- 目标用户、目标地区、时区及浏览器范围已写明。
- 数据收集、保留、删除和支持流程已审核。
- 关键流程和异常路径通过验收。
- 并发预约保护经测试。
- 监控、告警、备份、恢复和回滚方式已验证。
- 支持入口、服务说明和预约规则对用户可见。
- 试用反馈和缺陷有分级与处理机制。

## 5. 风险与应对

| 风险 | 早期信号 | 当前应对 |
|---|---|---|
| 不同教练的规则差异过大 | 每次访谈都要求不同流程 | 先限定目标细分，不急于全部配置化 |
| 可用时段不可信 | 教练继续私聊确认或频繁手工纠错 | 优先打磨排期与冲突处理 |
| 学员不愿注册 | 手机流程在登录处大量中断 | 将学员账号列为显式决策，优先验证免注册路径 |
| 通知不可靠 | 已成功预约但双方以为失败 | 结果页为事实来源，通知可追踪且可恢复 |
| 范围被支付/营销拖大 | 核心预约未验证即开始大量集成 | 以最小闭环作为阶段门槛 |
| 隐私或越权问题 | 链接可猜测、教练看见他人数据 | 数据隔离与安全凭据列为验收项 |
| 时间处理错误 | 跨时区或临界点出现错约 | 先明确市场和时区规则，集中处理时间语义 |

## 6. 后续候选路线（不代表承诺）

只有试用证据明确时再排序：

- 支付、退款与对账。
- 外部日历同步。
- 自动提醒与消息模板。
- 团课容量、候补名单。
- 套餐与学员关系管理。
- 多教练组织与分级权限。
- 教练经营分析。
