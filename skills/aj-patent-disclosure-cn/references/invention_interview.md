# 发明访谈：逐轮挖掘与内容确认

## 使用范围

用于专利点挖掘、新交底书起草和改变核心保护主线的修订。目标是让双方对真实机制、证据和拟保护范围形成一致理解。不要追求固定访谈轮数，也不要把提问数量当作质量指标。

## 1. 先取证，再选择当前问题

先阅读已提供的资料并复用已确认内容。用数句话说明已知技术链、证据边界及当前最影响判断的缺口，不把整个底稿倒给用户。

在底稿中维护有依赖关系的问题：技术问题 → 实际机制 → 必要特征与效果 → 候选比较 → 起草依据。只问前置条件已明确的问题。优先处理会改变主线、导致虚构或阻断实施的问题；术语、版式等可自行处理。

每轮默认一个关键问题。至多三个互不依赖的简单问题可以合问；不要把五六个子问题包装成“一个问题”。根据用户的回答调整下一轮，不机械念问卷。

能从代码、文档和测试中查到的信息先自行查找。材料矛盾时，展示具体版本和冲突，让用户解释当前实际方案，不以最新文件名自动判定事实。

## 2. 提问方式

访谈中交替进行事实核实与主动建议。按 [主动发散与推荐](proactive_mining.md) 先自行研究并给出有理由的路线，避免连续要求用户提供“真正创新点”。中立原则适用于事实题；策略题应清楚表达推荐。阶段未通过不妨碍先展示带证据状态的机会卡。

每轮采用简短结构：

1. **当前理解**：复述刚确认的事实或新发现，并给出必要来源。
2. **为何要问**：说明这个缺口如何影响技术链、候选取舍或可实施性。
3. **本轮问题**：一个能由用户回答的具体问题，然后等待回应。

事实题用开放、中立的问法，允许“不清楚”“没有实现”“没有测试”。策略题才给选项、推荐和取舍。用户认可研发建议，只能记录为“同意探索”，不能升级成已实现功能；用户口述确认也不自动等于测试证据。

用户回答模糊时，围绕同一机制换成具体实例追问，避免用专业术语施压。回答“不知道”后，改为查材料、安排待补证据、缩小候选或给出有界草案，不无限循环追问同一句。

可按缺口选用以下追问，不一次全部展示：

| 缺口 | 有效追问 |
|---|---|
| 只有目标口号 | 最近一次出现这个问题时，系统具体发生了什么？ |
| 只有模块名 | 请按一条实际输入，说明该模块如何得到输出。 |
| 必要特征不清 | 如果去掉这一步，原来的技术问题会怎样变化？ |
| 常规组合 | 这些模块之间交换什么信息，使处理行为发生改变？ |
| 边界条件不清 | 输入缺失或该条件不满足时，当前实现实际走哪个分支？ |
| 效果无依据 | 这项改善来自什么对比或观察？没有测过也可以直接说明。 |
| 保护策略分叉 | A 覆盖主流程，B 聚焦反馈机制；结合证据与取舍，本次优先保护哪条主线？ |

不要问“你们是不是用了动态阈值，所以性能更好？”——这会把建议和效果一起塞进答案。

## 3. 两个内容核对节点

### A. 保护主线

先形成一至三个有来源支撑的候选，再给出比较：技术问题、必要特征及关系、效果及证据状态、检索状态、主要风险和建议定位。只有一个候选时也核对它是否代表用户希望保护的真实技术贡献，不为了凑数制造备选。

问题针对具体主线，例如：“本次以 P1 的队列反馈路由为主线，把 P2 的缓存规则作为从属限定，这是否符合你的保护重点？”不能只问“可以继续吗”。已经明确选择过的主线直接复用。

可在此之前检索已有材料支持的候选。检索发现区别消失或有更近文献时，展示具体影响，重新讨论受影响的取舍；不能悄悄换成材料中不存在的规避方案。

### B. 起草依据

完整起草前展示一屏左右的内容摘要：

- 一句话发明构思与选定主线；
- 要解决的技术问题与发明目的：分别核对现有不足和要达到的技术目标；
- 核心步骤、必要特征和一个端到端实施例；
- 区别特征、现有技术证据边界；
- 效果中哪些有实测、哪些只有机制依据；
- 不纳入本次正文的建议，以及剩余缺口的处理方式。

针对具体摘要核对遗漏或误解。若它只是重述本会话已逐项明确确认且没有变化的内容，记录依据后直接起草，不新增仪式性确认。材料齐全可以合并两个节点，材料篇幅多本身不代表双方理解已一致。

## 4. 停止条件与例外

进入完整起草的条件：主线已经明确；必要技术链和一个实施例有依据；效果措辞符合证据；影响实施或主线的矛盾已解决；剩余缺口可安全排除或已有处理方式。没有量化实验不必无限追问，可以在机制有据时仅描述定性效果。

用户明确授权代选、要求一次成稿或终止访谈时，复用其授权。能够据已有材料完成的部分继续做；缺失必要事实时输出标为“审阅草案”的产物和独立缺口报告，不调用终稿导出来包装未完成内容。普通的“帮我生成交底书”不等于这种例外。

事实确认不是新颖性、创造性结论；用户说“这个肯定没人做过”不能替代检索。只做格式转换、读专利等局部任务时，不启动无关的完整访谈。

## 5. 保存可恢复的状态

完整案件按 [五阶段工作流](staged_workflow.md) 保存阶段 JSON、确认记录和自动生成的确认页，不重复手写 `interview_state.md`。仅未初始化工作流的轻量任务可在项目输出目录 `reports/interview_state.md` 保存下列精简状态，短对话可直接维护在会话中。不要保存到 skill 模板目录，也不把访谈记录嵌入正式交底书。

```markdown
# 访谈状态
- 当前阶段：事实澄清 / 候选比较 / 起草依据 / 起草
- 本轮已明确内容：事实或决策、用户回答或材料定位
- 已选主线：候选 ID、理由、确认依据或用户代选授权
- 关键缺口：问题、依赖项、阻断哪些工作、状态
- 尚未解决的材料冲突：来源、版本、影响
- 暂不纳入：研发建议、无据效果、非关键缺口及原因
- 下一问：一个问题及它为什么优先
- 起草依据：已确认摘要的版本、尚待核对的变化
```

中断恢复时先读状态与新增材料，只核对变化。新增事实改变主线、实施例、效果或检索结论时，标记受影响的旧判断并更新相关产物，不重新问全部问题。

## 6. 简短示例

用户：“我们用模型智能调度任务，帮我挖专利。”

首轮：“目前只能确定模型用于任务调度，还不知道它解决的具体技术问题。请讲一次现有调度出问题的实际场景。”

用户：“低电量设备接到大任务会来不及完成。”

下一轮：“问题涉及低电量下的任务超时。你们当前实现如何决定任务留在本机还是转移？请用一次实际任务说明。”

如果用户答“自动选最优”，继续澄清决策依据，不能自行补入强化学习、奖励函数或阈值。如果答“还没做”，把它保留为研发构想，不写成已实现实施例。
