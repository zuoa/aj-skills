# 项目材料扫描与证据化访谈

## 目标

从需求文档、设计稿、代码、测试记录和既有 Office 文件中提取可核验的发明事实，同时保留来源定位。扫描的目的不是“读完整个仓库”，而是建立足以支撑技术链、实施例和拟保护特征的证据底稿。

## 一、扫描前固定边界

记录以下信息：

- 项目根目录或材料清单；
- 当前代码版本、Git commit 或材料日期；
- 申请主题与不纳入本案的模块；
- 检索截止日、已公开时间和公开方式；
- 哪些内容属于商业秘密，不准备在申请中公开；
- 用户希望的交付范围：挖掘、检索、草案、审校、附图或 Word。

如果目录很大，先列文件树并按关键词定位，不要逐文件漫读。

## 二、材料优先级

| 优先级 | 材料 | 重点 |
|---|---|---|
| 1 | 已有交底书、专利点表、评审结论 | 已确认边界、历史版本、已知冲突 |
| 2 | 详细设计、架构、接口和数据协议 | 模块关系、数据流、控制流、状态转换 |
| 3 | 核心实现与测试 | 实际执行步骤、条件分支、异常处理、效果证据 |
| 4 | 需求、会议纪要、PPT | 问题来源、方案演进、待确认假设 |
| 5 | 运维与观测材料 | 部署约束、性能瓶颈、故障与恢复机制 |

默认排除第三方依赖、生成文件、构建产物、压缩包、锁文件、日志全集和与主题无关的资源文件。不要读取或回显密钥、令牌、密码、个人敏感信息；若意外发现，只记录“存在敏感配置，需要排除”，不复制其值。

## 三、Office 材料

`.docx`、`.pptx` 或 `.ppsx` 不能因读取不便而漏掉。需要转为可检索文本时运行：

```bash
python3 scripts/office_to_markdown.py \
  <材料1.docx> <材料2.pptx> \
  --output-dir <转换目录> \
  --manifest <转换目录>/office_manifest.json
```

脚本只使用 Python 标准库，提取正文、表格、幻灯片文本、备注和嵌入媒体，不执行文档中的宏或外部链接。转换结果是内部扫描材料，不应原样作为交底书正文。

旧版 `.doc`、`.ppt` 和扫描型 PDF 无法由该脚本可靠提取。此时明确列为待转换材料；有 OCR 或文档读取工具时再处理。

## 四、证据清单

对影响技术链或保护范围的信息建立清单：

| ID | 技术事实 | 状态 | 来源定位 | 时间/版本 | 关联特征 | 冲突/缺口 |
|---|---|---|---|---|---|---|
| E1 |  | 用户已确认/资料有据/合理推断/待确认/建议方案 | 文件:行、页、图、提交或测试编号 |  | F1 |  |

来源定位优先使用：

- Markdown/代码：相对路径与行号；
- Word/PPT：原文件名、页/幻灯片号、转换稿小节；
- 测试：报告名称、数据集、时间、版本和基线；
- 对话：本轮用户明确确认的表述；
- 图片：图名、页码和必要的图元描述。

不要把注释、未调用代码、废弃分支或产品规划自动视为已实现功能。代码只能证明“该版本存在某实现”，不能单独证明部署状态、性能效果或首次公开时间。

## 五、从材料反推技术链

按以下顺序提取：

1. 触发条件和输入对象；
2. 核心步骤、模块和先后/反馈关系；
3. 中间数据、状态或控制量；
4. 输出如何作用于设备、网络、存储或后续计算；
5. 异常、回退、边界与部署约束；
6. 技术效果及其证据条件。

每个拟保护特征至少需要一个来源定位。没有来源的内容进入 `合理推断`、`待确认` 或 `建议方案`，不得因“技术上合理”直接写成既有事实。

## 六、冲突处理

当文档、代码、测试和用户表述冲突时：

1. 保留各版本原说法和来源；
2. 判断冲突是否改变必要特征、实施例或效果；
3. 优先请求用户确认当前有效版本；
4. 未确认前不要静默选择对自己写作最方便的一版；
5. 已废弃方案可作为演进背景，但不得与当前方案混写。

## 七、最小访谈

扫描后只问会改变技术实质的 3–5 组问题，优先覆盖：

- 当前真正投入使用的步骤/模块关系；
- 与旧方案相比新增或改变了什么；
- 关键阈值、参数选择依据和异常路径；
- 效果由哪些测试、日志或机理支持；
- 哪些细节准备公开，哪些倾向保密。

不要优先追问联系人、申请人、字体、页边距等非技术信息。

## 八、输出

材料扫描阶段输出：

1. 材料覆盖范围与未读取项；
2. 证据清单；
3. 一条最小可实施技术链；
4. 候选必要特征及来源定位；
5. 冲突与披露缺口；
6. 需要用户确认的 3–5 个问题；
7. 可进入专利点挖掘、检索或起草的结论。
