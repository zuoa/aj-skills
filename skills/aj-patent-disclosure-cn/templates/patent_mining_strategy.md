# 证据驱动的专利点挖掘

## 目标

从用户已经完成或能够确认的技术方案中识别可保护的技术构思，并区分核心构思、从属限定、组合/分案候选和后续研发建议。挖掘质量取决于技术因果链和披露证据，不取决于轮数或候选点数量。

## 一、挖掘边界

先建立事实表：

| 信息 | 内容 | 状态 | 来源 | 对保护范围的影响 |
|---|---|---|---|---|
| 技术问题 |  | 用户已确认/资料有据/合理推断/待确认 | 对话或文件位置 |  |
| 核心手段 |  |  |  |  |
| 技术效果 |  |  |  |  |

遵守以下边界：

- 只把 `用户已确认` 和 `资料有据` 的内容视为既有发明事实；
- `合理推断` 必须显式标注并请求确认；
- `建议方案` 单列为研发方向，不能为了显得“更有创新”而写入既有实施例；
- 常规技术名词、业务目标、应用场景和效果口号本身不是专利点；
- “跨领域组合”只有在产生新的技术相互作用和可解释效果时才可能成为候选。

## 二、四遍挖掘法

### 第一遍：锁定问题—手段—效果链

用一句话填写：

```text
为解决 [具体技术问题]，通过 [必要技术特征及其关系]，
使 [处理对象/系统状态] 发生 [可解释变化]，从而获得 [技术效果]。
```

检查：

- 技术问题是否来自现有技术不足，而非“提升体验/增加收入”等业务目标；
- 技术手段是否包含可执行步骤、结构或关系，而非“智能模块/优化算法”；
- 技术效果是否能由这些特征产生；
- 删除任一特征后，问题是否仍能解决。若能，该特征通常不是独立构思的必要特征。

第一遍输出 1–3 个“独立构思种子”，而不是追求十几个名称不同但内容重叠的点。

### 第二遍：分解技术机制

围绕每个种子按实际方案选择相关维度：

- 输入或采集：数据/信号从何而来，字段、格式、时序、质量控制；
- 预处理：过滤、编码、归一化、特征构造、分片或加密；
- 核心处理：算法步骤、模型结构、控制逻辑、协议或数据结构；
- 模块协作：调用顺序、消息、状态、反馈和同步机制；
- 输出应用：输出如何驱动设备、网络、存储、显示或后续计算；
- 异常路径：缺失数据、超时、冲突、攻击、漂移和降级；
- 部署约束：端/边/云划分、算力、带宽、能耗、延迟和隐私。

每个候选都要写成“特征 + 关系/动作 + 作用机理”，避免只写名词。例如：

- 弱：`注意力机制`；
- 强：`依据实时网络状态生成上下文权重，并以该权重调整行为序列特征与内容特征的融合比例，使低带宽状态下的候选集生成减少高码率内容计算`。

第二遍输出：必要特征、可选特征、效果关联和披露缺口，并将候选标为“待检索”，不要在现有技术对比前称为已确认创新点。

### 第三遍：支撑保护范围

为核心构思寻找材料中已经披露的变化方式：

- 模块或步骤的等同替换；
- 参数典型值、范围和范围依据；
- 不同输入类型、数据结构或通信方式；
- 步骤的可并行、循环、批处理或流式实现；
- 训练/推理、在线/离线、端侧/服务端等部署变体；
- 正常、边界和异常场景。

这些变体用于判断上位概括是否有支撑。材料没有披露的变体放入“待确认/研发建议”，不要自动写成实施方式。

### 第四遍：形成布局

把候选分为：

1. **核心独立主题**：完整解决一个技术问题，包含必要技术特征组合；
2. **从属限定**：在核心主题上增加参数、结构、异常处理或部署约束；
3. **同构主题**：有正文支撑的方法、系统/装置、电子设备、存储介质、计算机程序产品；
4. **组合/分案候选**：解决不同技术问题或具有独立技术效果的另一构思；
5. **商业秘密候选**：难以检测侵权、公开后易被绕开或更适合保密的实现细节；
6. **研发建议**：值得补做但当前尚未完成的方案。

同构主题不是多个不同“专利点”，不要重复计数。

## 三、优先级评估

A/B/C/D 是内部布局优先级，不是法律结论。每项先给证据置信度，再评分：

| 维度 | 权重 | 核心问题 |
|---|---:|---|
| 区别强度 | 30 | 与已知方案相比，是否存在具体结构/步骤/关系差异 |
| 技术贡献 | 25 | 差异是否解决技术问题并产生可归因效果 |
| 披露成熟度 | 25 | 是否有足够细节、实施例、参数和证据支撑 |
| 战略价值 | 20 | 是否覆盖核心产品、容易检测、难以绕开 |

评分纪律：

- 未检索时，“区别强度”只能标记为待检索初评，不得假装是新颖性分数；
- 没有效果证据时降低置信度，不凭“看起来先进”打高分；
- 商业价值高不能弥补技术方案不完整；
- 文字相似度不进入评分。
- 有网络/数据库能力且任务目标包含寻找创新点时，应先完成相似专利对比和区别特征反向检索；没有实际检索时，候选最高只能标为“待检索初评”。

分级建议：

- **A**：核心构思清楚、披露较完整、与产品直接相关，优先检索和起草；
- **B**：有明确技术贡献，但仍需补证据或存在较近现有技术风险；
- **C**：适合作为从属限定、备选实施方式或外围布局；
- **D**：常规拼接、仅场景替换、缺少技术因果或尚属研发设想，暂不进入申请稿。

边界分数只能帮助排序，最终级别必须附理由和置信度。

## 四、用户确认点

只在会改变独立构思或引入新事实时请求确认：

- 哪个技术问题是本次申请的主问题；
- 哪些特征是实际已经实现，而非建议；
- 必要特征组合是否准确；
- 哪些实现细节准备公开，哪些希望保密；
- 多个构思合并、拆分或分案的策略。

可用以下简表，避免展示数十个未经筛选的候选：

| 候选 | 技术问题 | 必要特征 | 效果 | 状态/证据 | 建议 |
|---|---|---|---|---|---|
| P1 |  |  |  |  | 核心独立主题 |
| P2 |  |  |  |  | 从属限定 |

## 六、常见失败模式

- 把 LSTM、区块链、知识图谱等已知技术名词直接列为创新点；
- 把两个流行技术相加，却不说明交互关系和新增效果；
- 因为换到医疗、金融或教育场景就生成新专利点；
- 自动扩展到几十个候选，导致核心构思被稀释；
- 用虚构的相似度、专利号或授权率筛选；
- 为补足实施例而发明用户没有实现的模块、数据或实验结果；
- 把方法、系统、介质等同构主题重复当成不同创新点；
- 只谈商业价值，不检查能否实施和是否容易检测侵权。
