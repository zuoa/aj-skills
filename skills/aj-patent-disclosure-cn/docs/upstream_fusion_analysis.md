## 一、上游架构

上游不是单一提示词，而是三层结构：

1. `SKILL.md`：负责模式识别、工具路由和总体顺序；
2. `prompts/`：把交底书、迭代和专利解读拆成独立步骤；
3. `tools/`、`references/`、`assets/`：提供 Office 转换、国知局检索、Mermaid/Word、PDF 抽取、Obsidian 入库和知识图谱。

它实际包含三套工作流：

- 从项目材料到技术交底书；
- 在已有交底书上增量合并或纠错；
- 把已有专利解读为 Obsidian 笔记和知识图谱。

## 二、上游最值得吸收的能力

### 1. 面向真实项目材料

上游明确要求扫描设计文档、代码、Word 和 PPT，而不是只接受用户整理好的技术描述。这能显著降低“交底书写得顺，但没有项目证据”的风险。

### 2. 任务模式隔离

“写交底书”“读专利”“改已有稿”采用不同入口，避免用户只想改一段时重新跑完整挖掘，也避免把专利解读误当成交底书生成。

### 3. 非破坏性迭代

上游强调新时间戳文件、保留旧稿和修订对话记录。这对专利稿多轮协作很重要，因为事实、保护重点和检索结论会反复变化。

### 4. Office 和可交付工具链

Word/PPT 转 Markdown、Mermaid 转图、Markdown 转 Word，使工作流不仅“会写”，还能够处理常见输入并形成可修改的交付物。

### 5. 专利解读的证据结构

权利要求树、从属权新增限定、说明书段落和附图对照，是比普通摘要更有价值的阅读方法，也能反哺现有技术对比。

### 6. 交付卫生

上游对内部自检不进入正文、工具实现痕迹不进入交付稿、脱敏、公式和跨章节一致性有明确约束。

## 三、上游的局限与风险

### 1. 专利点挖掘偏“先列候选”

上游默认列 3–5 个候选，并允许基于材料适度推演；如果事实边界不严，容易把合理研发建议写成已经完成的发明。其“创新性、可授权性”排序也缺少足够严格的证据置信度约束。

### 2. 查新流程过度绑定单一站点

国知局公布公告站浏览器自动化脚本依赖页面 DOM、WAF 等待和 Playwright。它有实际价值，但脆弱、耗时、依赖较重，并包含降低自动化特征的实现。把它设为通用 skill 的强制主路径，会增加失败面和维护成本。

### 3. 摘要使用规则仍可能过强

上游要求充分使用检索结果中的摘要，这适合初筛，但复杂的特征关系、新颖性和创造性仍必须回到权利要求与说明书全文。

### 4. Obsidian 子系统过重

专利阅读子系统代码量很大，覆盖 PDF 获取、附图裁切、Canvas、术语网、线索旁注和库初始化。它适合个人知识库产品，但会显著扩大交底书 skill 的依赖、触发范围和维护责任。

### 5. 主提示存在强制流程过多的问题

生成全文前必须查新、默认预览、固定章节、固定交互提示等规则，对某些局部任务会造成额外步骤。一个强 skill 应先路由任务，只执行必要分支。

### 6. 与本地 skill 的重复和冲突

本地 skill 已具有更严格的事实状态、充分公开、支持矩阵、单一文献新颖性分析、创造性问题—启示链和 AI 专项门槛。直接合并上游全文会重复规则，并削弱本地证据纪律。

## 四、融合决策

| 上游能力 | 决策 | 本地落点 |
|---|---|---|
| 项目/代码/Office 扫描 | 吸收并强化 | `project_material_intake.md`、`office_to_markdown.py` |
| 交底书预览 | 吸收为可选阶段 | `SKILL.md` 起草路由 |
| 增量合并与纠错 | 吸收并增加影响传播 | `revision_and_redaction.md`、`revision_log.py` |
| 脱敏 | 吸收，避免过度抽象 | `revision_and_redaction.md` |
| 权利要求树与证据对照 | 吸收为轻量专利阅读模式 | `patent_reading_and_claim_mapping.md` |
| 国知局浏览器/WAF 工具 | 不复制 | 继续采用多来源检索和证据核验；官方文本优先 |
| Mermaid/Word 全套替换 | 不替换 | 保留本地结构化 JSON、校验、附图和 DOCX 工具 |
| Obsidian/Canvas 私库 | 不并入 | 避免偏离交底书核心；后续可拆成独立 skill |
| “3–5 个候选”固定数量 | 不吸收 | 保留本地 1–3 个独立构思种子和证据分级 |
| “可授权性”直接排序 | 不吸收 | 保留证据置信度与风险措辞，不给授权概率 |

## 五、融合后的能力边界

增强后的 skill 支持五类任务：

1. 从零散描述做发明访谈和专利点挖掘；
2. 从项目目录、代码、Word/PPT 和测试材料建立证据底稿；
3. 对已有专利做权项—说明书—附图证据化解读；
4. 进行现有技术检索、单文献特征对照和区别特征反向检索；
5. 生成、审校和非破坏性修订交底书，并输出附图、Markdown、DOCX 和修订记录。

核心判断仍遵循本地原则：事实与建议分离，区别特征不自动等于创新点，摘要不代替全文，技术效果必须可归因，未实际检索不得声称新颖性或创造性。
