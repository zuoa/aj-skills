# 阶段流程与交互规则

| 阶段 | 要解决的问题 | 产物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 1 主题 | 什么业务、谁看、为什么看、展示还是值守 | 主题、视觉风格、屏幕条件、必备与排除项 | 主题与风格已指定、已确认或明确授权代决 |
| 2 色彩 | 品牌、背景、文本、强调及状态如何呈现 | 色板预览、完整 token | 配色确认或授权代决 |
| 3 布局 | 信息主次、面积分配与阅读顺序 | 预设 ID 或自定义意向、线框 | 预设确认则到 5；自定义则到 4 |
| 4 自定义 | 列数、比例、地图/主图、区块数量 | customLayout、线框 | 参数确认、配置检查通过 |
| 5 空框架 | 主题、配色和结构组合是否合适 | 无内容可运行预览、截图、版本 | 本版本确认或明确授权代决 |
| 6 内容 | 指标体系、正文、来源、口径、可用数据 | 内容清单、来源/槽位映射 | 关键冲突解决，结构修改经过回退确认 |
| 7 整合 | 内容填入框架、接口及状态可运行 | 完整页面、代码与交付候选 | 可进入核验 |
| 8 核验 | 是否符合确认要求、数据和页面是否正确 | 验收记录、修订、最终交付 | 必验项通过，未执行/待补项如实披露 |

每次开工读 `screen-brief.json` 和现有文件，确认当前阶段及仍有效的决定。没必要为 API 适配任务重新选主题，也不能在新建任务中把旧示例当成用户决定。

## 每轮交互

先给业务建议，再请用户决定；每个候选用一句话说明结果及代价。默认每轮一个决定，已给完整要求时可批量复述并记录。不要一次抛出几十个问题。

主题阶段同时参考 [视觉风格目录](style-catalog.md) 给 2–3 个形态不同的候选，记录在 `stages.visualStyle`，不增加强制新轮次。

例：主题阶段给“经营复盘（推荐）—总量/趋势/结构”“运行值守—状态/异常/处置”，允许直接填写主题/受众/目的。颜色阶段给色块或 HEX，不能只说“高级科技风”。布局阶段给线框和是否含地图，不能只列“方案 A/B/C”。

没有问答工具时用编号候选并明确“也可直接描述”。不能要求用户为了自定义先修改 JSON；由代理把描述转为配置。用户说“3 列、1:2:1、中间地图”后只问缺失的行区块和顶部/底部；说“别问，照你推荐做”则记录授权范围后推进。

## 确认与版本

决定状态使用 pending、proposed、confirmed、delegated、invalidated。confirmed 包括用户直接指定；记录原话摘要、消息依据或确认日期。delegated 记录授权语句与范围，不伪造用户看过页面。流程执行结果另用 pass/fail/not-run，不与决定状态混用。

阶段 5 的确认指向具体版本和配置；至少记录 framework.json 及实际 style/layout/palette 的版本或摘要、预览 URL/截图。候选切换、导出、代码检查和浏览器自检都不是确认。导出的 JSON 只含配置，不承载通过状态。

等待必要回答时可做不依赖回答的资源梳理，不能提前绑定指标或偷偷采用默认值越过关口。最后只问本阶段尚缺的一项，不为已授权的本地修改再要权限。

## 变更与回退

| 变更 | 保留 | 重新检查 |
| --- | --- | --- |
| 主题/用途变化 | 仍适用来源、接口和底层协议 | 配色、布局、框架及内容体系 |
| 风格形态变化 | 仍适用业务主题、指标、接口、配色和布局 | 标题/面板/图表形态、框架和完整页；资产变化另审 |
| 配色变化 | 布局、指标和接口 | 色彩可读性、框架配色及完整页 |
| 位置/列数/地图变化 | 已确认内容与接口 | 自定义参数、框架、槽位映射与页面 |
| 指标/内容变化 | 仍适用主题、色板和框架 | 口径、绑定、图表及容量；装不下再回退布局 |
| 接口或实时值变化 | 视觉决定与稳定绑定 | 契约、数据核对、异常和刷新 |

将被影响的确认标为 invalidated，记录原因和替代版本。不要让已确认状态指向一个后来被修改的配置。
