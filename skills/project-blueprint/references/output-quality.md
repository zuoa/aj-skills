# Blueprint output quality

蓝图是供团队做决定和验收的技术文档，不是演示稿、广告文案或聊天回复。正文应直接、克制、可追溯。

## 写作规则

- 从事实、决定、理由或缺口开始，不写“当然”“好问题”“希望有帮助”一类对话残留。
- 使用稳定术语和具体动词。一个动作在需求、界面文案和验收场景中保持同名。
- 只在确有比较关系时使用表格；简单结论用短段落或列表，不为整齐强行凑成三项。
- 不用“无缝、强大、智能、高级、行业领先”等词替代可观察行为，也不夸大普通功能的意义。
- 不写“业内普遍认为”“最佳实践表明”等模糊归因。需要外部依据时给出具体来源；没有依据时写成建议或待决定项。
- 不制造指标、用户反馈、案例、引用、测试结果或精确数值。未知信息使用 `provisional` 或 `TBD-*`。
- 避免过量粗体、破折号、内联小标题和重复总结。标题表达内容，不承担装饰作用。
- 保留必要的不确定性，但直接说明缺什么、由谁决定、阻断什么，不写泛化免责声明。

## Emoji 与装饰符号

团队编写的蓝图、产品 UI、系统文案、标题、列表标记、按钮、状态和导航默认不使用 Emoji。Emoji 的平台外观和辅助技术名称不稳定，也容易让正式产品产生模板化或聊天机器人语气。

以下情况可以例外：

- 用户生成内容需要原样保存或展示。
- 已确认的品牌语言明确使用某个 Emoji。
- 社交、游戏、儿童或表达性产品中，研究或现有产品事实证明 Emoji 对用户任务有价值。

例外必须记录在 `DESIGN.md`：使用位置、用户价值、批准人或状态、文本或标准图标替代方案。Emoji 不得是操作、状态或含义的唯一载体，也不得替代可访问名称。校验器仍会报告 warning，供评审者逐项核对。

使用图标时选择一个与平台匹配的统一图标体系。图标表达熟悉、单一的含义；不熟悉或关键操作配可见文字，纯图标按钮提供可访问名称。

## 交付前编辑检查

- 每一节是否改变了范围、行为、设计、实现、运行或验收决定？不能则删减。
- 是否把假设、推荐或未知写成了事实？修正状态和来源。
- 是否出现与项目无关的通用卖点、模板页面或视觉套路？删除或补充任务依据。
- 是否存在装饰性 Emoji、符号、粗体或重复结构？删除；确需 Emoji 时登记例外。
- 错误、空状态和限制是否具体说明发生了什么以及下一步？
