# 周报与月报

运行环境：Python 3.10+ 和本地浏览器。报告生成由当前 agent 完成，无需模型 API 或第三方 Python 依赖。

将材料整理成有依据、可跨期追踪的汇报。周报关注进展、近期节点和纠偏；月报关注目标达成、指标变化和下月安排。默认输出 Markdown，正文采用纵向条目，不标注来源或本机路径。

## 资源与执行位置

- 先读 [数据契约与分析规则](references/data-contract.md)，按其结构提取材料。
- 首次建账、目标变更或材料不足时读 [补充服务与恢复流程](references/service-workflow.md)。
- 生成周报读 [周报模板](references/weekly-template.md)；生成月报读 [月报模板](references/monthly-template.md)。
- 需要调整汇报方法时参考 [实践依据](references/best-practices.md)。

以下命令中的 `<skill-dir>` 替换为本 SKILL.md 所在目录。`<workdir>` 是用户业务的汇报工作目录；在其下保存 `.weekly-report/`。周报、月报及各月份共用此目录，避免将台账建在每个月的材料子目录中。不要把业务数据写入安装的 skill 目录。

## 1. 确认周期并读取材料

1. 识别周报/月报、起止日期和统计截止日。默认周范围为周一至周日、月范围为自然月，时区沿用用户环境。当前周期尚未结束时，截止日取当前日期。只有 `202605` 时可认作 2026 年 5 月；“5 月周报”不能定位某周，需确认具体范围。
2. 用户未给材料路径时，先扫描当前目录及下一层目录，依次匹配 `202605/`、`2026-05/`、`2026年5月/` 及含该周期的目录；唯一候选直接使用，多候选才询问。文件搜索优先使用 `rg --files`，排除 `.weekly-report/` 和已生成报告，防止输出再次成为本期事实。
3. 识别本期部门总结、规划、上期报告和已有台账。材料周期以内容为准，修改时间只作为异常线索。没有规划时允许浏览器建立基线；没有上期报告时按首次汇报处理。
4. 读取 MD/TXT；按环境已有文档工具提取 DOCX、PDF、XLSX/CSV，不依赖不存在的 skill 名称。无法读取、内容过期或统计口径冲突时保留具体异常问题，不能将文件视为已覆盖。

只从用户提供或可读取的材料提取事实，不为生成业务汇报搜索互联网。研究参考已经随 skill 保存。

## 2. 建立逐项跟踪输入

读取 `.weekly-report/ledger.json` 的已确认与待确认目标，并参考历史周期快照。匹配已有目标的稳定 ID；名称相似但交付物不同的事项不要合并。规划、上期承诺和遗留风险都要覆盖，按部门与具体交付逐项建账。

将本期目标、进展和具体补充问题写入工作目录中的 `report-input.json`，执行：

```bash
python3 <skill-dir>/scripts/report_workflow.py prepare --workdir <workdir> --input <workdir>/report-input.json
```

脚本自动继承活跃目标，生成首次/变更确认及状态、进展、日期、指标口径等缺口。下期计划、风险处理、专题、依赖和材料异常不能仅靠这些固定字段判断：逐项加入 `questions`，写清需补什么及判断用途。

同一字段存在冲突时，将其值留空，问题背景写清不同说法，再收集可用于该字段的确认结果。不要选择对报告更有利的数字。新时间节点是预测还是承诺调整必须分清：预测写 `forecast_date`，只有明确提出调整承诺时才修改目标的 `deadline`。

## 3. 浏览器补充与确认

- `status=draft`：启动服务，逐项确认首次基线、目标调整和资料缺口。每个目标及计划中缺少材料的事项有独立输入区域，不用一个总文本框代替。
- `status=ready`：已有基线且材料完整，无需打开页面，可直接 merge。
- 已有本期会话时不要再次 prepare 或覆盖草稿，先 status，再按已保存状态继续。

```bash
python3 <skill-dir>/scripts/report_workflow.py serve --workdir <workdir> --period <period-id>
```

使用后台进程或可持续的工具会话启动。默认尝试打开浏览器，并输出完整本地链接。工具环境禁止 GUI 时按环境规则申请执行权限；不能用无浏览器模式悄悄省略用户界面。打开失败则将完整链接交给用户访问。

每项必须填写，或明确选择“暂无法提供/确认”并说明原因。不要替用户勾选确认。可以保存草稿、刷新恢复、添加新目标或下期计划。提交前不能生成最终报告。

运行 `status` 短间隔检查（每次等待不超过 30 秒），等待时向用户说明进度。提交后当前会话继续，不再额外请求生成许可。如果用户暂时离开或会话中断，保留 draft；以后调用可恢复。服务或浏览器不可用时保留待补充状态并说明具体阻碍，不静默生成。

## 4. 合并、分析并生成

```bash
python3 <skill-dir>/scripts/report_workflow.py merge --workdir <workdir> --period <period-id>
```

读取本期目录中的 `analysis.json`、`confirmation.md` 和需要的历史快照，按对应模板生成主报告。脚本计算事实覆盖、指标差额和可计算的时间偏差；agent 结合业务背景解释影响、梳理风险和编写下期计划。

分析时遵循：

- 区分完成状态、时间状态和资料覆盖。“未提及”不等于“未完成”，“未到期”不等于“按计划”。
- 逐项展示目标/验收标准、原始与当前节点、实际结果、实际或预计日期、偏差和后续动作；未确认基线不能用于达成判断。
- 只对相同单位、口径、统计范围和数值类型的数据计算目标差额。月报不能将周报累计数重复相加；没有完整月度数据就收集确认。
- 没有阶段计划时，不按时间经过比例推断应有进度；不把收入、验收额、回款额相互替代。负数、零目标、越小越好指标按数据契约处理。
- 每项偏差尽量给出原因、影响、纠偏动作、责任人和时间。未知原因或日期保留判断限制，不编造。建议明确标为建议，不能写成已承诺计划。
- 跨期比较只用相同报告类型、此前已结束且不重叠的周期。环比与同比需要可比数据；不满足时省略数值比较并说明限制。
- 已明确暂无法提供的事项在主报告披露其影响范围；具体问题和原因放入独立记录。正文不展示内部核对明细和材料文件名。
- 摘要 3–5 句话，统计数量与 analysis 一致。禁用“基本完成、大体上、整体良好、稳步推进、有序开展”等掩盖事实的词语。

保存 `{周期}-周报.md` 或 `{周期}-月报.md`，将 `confirmation.md` 复制为 `{周期}-人工补充与确认记录.md`。再归档最终报告：

```bash
python3 <skill-dir>/scripts/report_workflow.py finalize --workdir <workdir> --period <period-id> --report <report-path>
```

输出报告链接，简述重要偏差与仍有的判断限制。完成后终止本次启动的服务；等待用户填写时不停止服务。不要终止不属于本次会话的进程。

## 验证与修订

完成前检查：台账目标是否全部有本期结果或明确未知，未到期目标是否被误判，日期调整是否保留原始承诺，指标是否可比，下期计划是否有负责人和时间，来源信息是否只留在内部。

已归档报告不可原地覆盖。追加材料或发现错误时，以 `原周期-r2` 等新 ID 建立修订会话，保留原报告；后续趋势按实际日期选择最近已结束周期，不能将修订版重复累计。
